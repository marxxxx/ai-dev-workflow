# Ticketing System: Gitea Issues

This file is the single source of truth for how every agent interacts with the ticketing system.
It is generated from `agent-src/includes/ticketing-gitea.md` for `{{project.name}}`. To switch the
project to a different backend (for example file-based tickets), change `ticketing.backend` in
`ai-project.json` and regenerate — do not edit this file by hand.

## Repository

All issues are managed in the `{{repo.slug}}` repository on the Gitea instance registered under the
`tea` login `{{ticketing.gitea.login}}`.

## CLI Tool

**Always use the `tea` CLI via the Bash tool for ALL ticketing operations.**

Every command below passes `--login "{{ticketing.gitea.login}}" --repo {{repo.slug}}` explicitly, so it
targets the right server and repository no matter which git remotes are configured. Two rules that go
with that:

- **Run them from inside the project's git working tree.** `tea` resolves the local repository first
  and aborts with `git rev-parse --show-toplevel: fatal: not a git repository` outside one — even when
  `--repo` is given. This is never a problem in normal work; it matters if you ever shell out from a
  scratch directory.
- **Keep the quotes around the login value.** `tea` profile names may contain spaces, and an unquoted
  one is split into two arguments (`Error: login name '…' does not exist`).

Prerequisite (one-time, per machine — a human does this, not an agent): `tea` must be on `PATH` and the
login profile must exist. Verify with `tea logins list`; if the command is missing or
`{{ticketing.gitea.login}}` is not listed, stop and ask the human to install `tea` / run `tea login add`.
Do not attempt to install the CLI, create a login, or handle tokens yourself.

The commands below are verified against **tea 0.15.1**. If one is rejected as an unknown command or
flag, report `tea --version` to the human instead of improvising an alternative — a differing CLI
version is the likely cause, and inventing a different command risks a wrong ticket mutation.

## Issue Status Labels

Statuses are stored as Gitea labels on the issue.

**Precondition — verify once per session, before the first query.** Gitea filters silently on unknown
labels: `--labels "a-label-that-does-not-exist"` does not error and does not return nothing, it drops
the filter and returns **every** open issue. A missing status label therefore turns "list the tickets
ready for development" into "list everything", and acting on that result would mutate unrelated
issues. So:

```bash
tea labels list --login "{{ticketing.gitea.login}}" --repo {{repo.slug}}
```

All six status labels below must be present. If any is missing, **stop and ask the human** to create it
(`tea labels create --login "{{ticketing.gitea.login}}" --repo {{repo.slug}} --name "…" --color "…"`) —
do not proceed with a label-filtered query, and do not create the labels yourself.

**Belt and braces.** After any `--labels`-filtered query, confirm each returned issue actually carries
the label you asked for (the `LABELS` column, or the `labels` array with `--output json`) before acting
on it. If it does not, the filter was dropped — treat the result as unusable and report it.

| Status Label | Meaning | Set By |
|--------------|---------|--------|
| `{{status.new}}` | Ready for development | Product-architect (on issue creation) |
| `{{status.in-progress}}` | Developer actively working | Developer (before starting work) |
| `{{status.review}}` | Implementation complete, awaiting code review | Developer (after implementation) |
| `{{status.test}}` | Code review passed, ready for QA testing | Orchestrator (after review passes) |
| `{{status.acceptance-test}}` | Automated workflow complete, PR open | Orchestrator (after QA passes) |
| `{{status.failed}}` | Code review or QA testing found issues | Orchestrator (on review/test failure) |
| **Closed** | Human has verified and accepted | **Human only — NEVER closed by automation** |

## Upstream Ticket

An issue may originate from an **upstream ticket** in another backend (for example an Azure DevOps
Product Backlog Item). Gitea issues have no formal relation type, so when the product-architect records
one, reference it as the first line of the issue body: `**Upstream:** <url-or-number>` (for example
`**Upstream:** https://dev.azure.com/org/project/_workitems/edit/12345` or `**Upstream:** AB#12345`).
This links the implementation issue back to the requirement's source and drives the feature-branch name
(see Git Branching Convention). It is optional: use `**Upstream:** None` when there is no upstream ticket
— the Gitea issue itself is then the single source of truth.

## Commands Reference

### Reading Issues

```bash
# View an issue
tea issues --login "{{ticketing.gitea.login}}" --repo {{repo.slug}} <number>

# View the comments on an issue (the workflow artifacts live here)
tea comments list --login "{{ticketing.gitea.login}}" --repo {{repo.slug}} <number>

# List issues by status
tea issues list --login "{{ticketing.gitea.login}}" --repo {{repo.slug}} --labels "{{status.new}}"

# List all open issues with metadata (machine-readable)
tea issues list --login "{{ticketing.gitea.login}}" --repo {{repo.slug}} --state open --output json
```

### Creating Issues

```bash
tea issues create --login "{{ticketing.gitea.login}}" --repo {{repo.slug}} \
  --title "[Issue Title]" \
  --description "## Overview
..." \
  --labels "{{status.new}}"
```

### Updating Issues

```bash
# Add a comment
tea comments add --login "{{ticketing.gitea.login}}" --repo {{repo.slug}} <number> "..."

# Transition status (remove the old label, add the new one — one command does both)
tea issues edit --login "{{ticketing.gitea.login}}" --repo {{repo.slug}} \
  --remove-labels "{{status.review}}" --add-labels "{{status.test}}" <number>

# Close an issue (HUMAN ONLY — agents must not do this)
tea issues close --login "{{ticketing.gitea.login}}" --repo {{repo.slug}} <number>
```

### Pull Requests

```bash
tea pulls create --login "{{ticketing.gitea.login}}" --repo {{repo.slug}} \
  --base {{git.prTarget}} --head {{git.branchPattern}} \
  --title "feat: [issue title] #[number]" \
  --description "..."
```

A human reviews, merges, and closes. Automation leaves the issue open at `{{status.acceptance-test}}`.

## Issue Comment Artifacts

The workflow hands context between agents through named issue comments:

- `{{artifact.implementationNotes}}` — posted by the developer after implementation.
- `{{artifact.reviewFeedback}}` — posted by the code reviewer when findings exist.
- `{{artifact.testResults}}` — posted by the QA engineer after acceptance testing.
- `{{artifact.handoff}}` — posted by the developer when a ticket does not fit one context window:
  everything a fresh developer needs to resume without re-exploring (see the handoff include). The
  most recent one wins; earlier ones are history.
- `{{artifact.costOrigin}}` — posted by the product-architect at creation, recording its session so
  the design cost can be attributed later (see the cost accounting include).
- `{{artifact.costSummary}}` — posted by the orchestrator when the ticket reaches
  `{{status.acceptance-test}}`: the token/cost breakdown for the ticket.

- [ ] Requirement 2

### Bug Issue Template

```markdown
**Upstream:** [upstream ticket URL/number, or None]

## Overview
[Brief description of the bug]

## Steps to Reproduce
1. Step 1
2. Step 2

## Expected Behavior
[What should happen]

## Actual Behavior
[What actually happens]

## Evidence
- Screenshots: [attach or reference]
- Console errors: [relevant error messages]

[Analysis of where the bug likely originates]

### Suggested Fix Approach
[High-level guidance on how to fix it]

## Acceptance Criteria
- [ ] Bug no longer occurs when following reproduction steps
```

## Git Branching Convention

- Branch name: `{{git.branchPattern}}` (for example `feat/42_user-login`).
- When the issue body records an upstream ticket (`**Upstream:**` line), the branch's first segment is
  the **upstream ticket number** instead of the implementation issue number — for example an
  `**Upstream:** AB#12345` issue uses `feat/12345_user-login`. With no upstream ticket
  (`**Upstream:** None`), use the implementation issue number as before.
- All implementation work happens on the feature branch.
- Merged into `{{git.prTarget}}` only after human acceptance.
